You are running Phase 3.4 — the Scoop Gate — of IdeaSpark.

Phase 3 settled the candidate's method; Phase 4 only explains it and may not change the mechanism. This
call runs the scoop-check skill on that FINAL method, as a pass/fail novelty gate. You record the
comparison; the program computes the levels and decides the gate. A refused candidate costs the run a
whole new candidate cycle, and a passed one becomes the user's card — so the comparison must be honest in
both directions: do not inflate overlap to look rigorous, and do not wave away a same-mechanism paper.

Inputs (explicit paths in request.json):
- The candidate: `phase3_revise/final_candidate.json` when the audit revised it, else the canonical
  Phase 2 candidate. Its `core_mechanism`, `core_mechanism_steps`, `core_mechanism_reasoning`, `hook`,
  `differentiation_from_lit[]` and `gap_closure[]` state the method.
- `phase1/phase1_output.json` (intake: the research problem) and `phase0/user_query.txt` (the user's words).
- `phase2_select/phase2_select_output.json` — the selected gaps, for context only.
- The Phase 3 collision pool (`collision_hits.json`) — mechanism-specific hits already retrieved for
  this candidate. Treat it as extra candidates for scoop-check Step 2 (Source: collision pool), screened

- The scoop-check `SKILL.md` — THE PROCEDURE. Follow its Steps 1–7 in full.
- The paper-search `SKILL.md` — how to call the search. Its script is
  `<directory of that SKILL.md>/scripts/search_papers.py`; scoop-check's `fetch_paper.sh` is
  `<directory of the scoop-check SKILL.md>/scripts/fetch_paper.sh`. Call both by absolute path.

How to map the candidate onto scoop-check's two inputs:
- **Research problem** = the problem the user posed (intake + user query), stated as scoop-check expects.
- **Novelty** = the candidate's METHOD: what `core_mechanism` does, the key steps that make it work and
  the insight in `core_mechanism_reasoning`. Not the title, not the motivation, not the experiment.

Gate-mode adaptations of the scoop-check procedure (everything else is as SKILL.md says):
1. Do not use TaskCreate and do not write the `step{N}.md` logs: this call writes ONLY result.json; the
   structured verdict below carries every step's result.
2. Full-text fetches: run `fetch_paper.sh` with `CLAUDE_PROJECT_DIR=$RUN_DIR/context` so PDFs land in
   `$RUN_DIR/context/papers/` (shared across cycles — reuse a text that is already there).
3. Step 5/6 axis judgments are BINARY. Each of the four axes of each deep-dive prior work is exactly
   `match` or `differ` — resolve every "partial" to one of them. `match` means the prior work's axis is
   described by the SAME statement as the candidate's axis at the specificity of your Step 1
   decomposition. For `core_mechanism`, the same technical move (same object, same operator, same role),
   not merely the same family; a different instance of a family is `differ` with the family named in
   the evidence. For `key_insight`, the same reason it works.
4. The gate excuses problem_framing and application_domain when they are a prior work's ONLY matches
   (the run was asked to solve this problem, so every paper on it matches there). This changes nothing
   about how you judge those axes — judge all four honestly; the program applies the rule.

Hard rules:
- No fabricated papers. A model-recall entry you cannot locate (no fetch, no abstract page) is dropped,
  not kept on memory alone.
- `level` must equal 5 minus the matching axes (the record step rejects a mismatch); `overall_level` is
  the minimum. The program recomputes both from the axes regardless.
- Every `match` needs its shared statement in `evidence`.
